# Tarot Mini App — Backend

## Стек
FastAPI + Pydantic + SQLAlchemy 2.0 + Alembic. Локально — SQLite (`tarot.db`,
один файл, без отдельной установки), в проде `DATABASE_URL` смотрит на
управляемый Postgres. Расклады, подписки и профиль персистятся в БД.

## Запуск

```bash
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env       # при необходимости отредактировать FRONTEND_ORIGINS / DATABASE_URL
uvicorn app.main:app --reload --port 8000
```

Таблицы создаются автоматически при старте (`init_db()` в `app/main.py`).

Проверить: `http://localhost:8000/health` → `{"status": "ok"}`
Документация (Swagger): `http://localhost:8000/docs`

## API

### `POST /api/spreads/draw`

Запрос:
```json
{ "spread_id": "love" }
```

`spread_id`: `"daily-card"` | `"love"` | `"future"` — те же значения, что в
`frontend/src/types/tarot.ts`.

Ответ:
```json
{
  "spread_id": "love",
  "cards": [
    {
      "position": 0,
      "position_label": "Прошлое",
      "card_id": "major-18",
      "name": "Луна",
      "arcana": "major",
      "is_reversed": false
    }
  ]
}
```

Каждый успешный вызов сохраняется в БД (`SpreadRecord`), привязанный к
Telegram-пользователю. Для `"daily-card"` повторный вызов в течение того же
календарного дня (UTC) не тянет новую случайную карту, а возвращает уже
выпавшую — иначе «карта дня» менялась бы на каждое открытие экрана.

### `GET /api/history`
Список раскладов текущего пользователя, новые сверху. Пустой массив, если
раскладов ещё не было.

### `GET /api/profile/stats`
```json
{ "total_spreads": 4, "days_streak": 2, "next_reward_day": 7, "next_reward_energy": 3 }
```
`days_streak` — число подряд идущих календарных дней (UTC) с хотя бы одним
раскладом, отсчитываемое от сегодня/вчера (в духе Duolingo: если сегодня
расклада ещё не было, но был вчера — серия не сбрасывается).

`next_reward_day`/`next_reward_energy` — ближайший непройденный порог серии
и его награда (`app/streaks.py::STREAK_REWARDS`, сейчас 7 дней → ✦ 3 и
30 дней → ✦ 10), оба `null`, когда все пороги текущей серии уже выданы.
Начисление происходит в момент расклада, который довёл серию до порога;
`POST /api/spreads/draw` возвращает выданное количество в `streak_bonus`.
Награда идёт в `purchased_energy`, потому что суточная энергия
перезаписывается на следующее утро и бонус за месяц дисциплины сгорел бы
к вечеру. Пороги внутри одной серии выдаются по разу, но сама серия
повторяема: прервалась и набрана заново — бонус придёт снова, иначе
вернувшийся пользователь оказался бы в худшем положении, чем новый.

### `GET /health`
Проверка живости сервиса.

## Архитектурный принцип
Весь выбор карт, случайность и ориентация — исключительно в `app/tarot/engine.py`
(`TarotEngine`). Frontend никогда не решает, какая карта выпала — только
отображает то, что вернул этот эндпоинт.

## Telegram initData
Все эндпоинты, кроме `/health`, ожидают заголовок `X-Telegram-Init-Data` (сырую
строку `Telegram.WebApp.initData` с фронтенда). Backend проверяет HMAC-SHA256
подпись и свежесть `auth_date` (см. `app/telegram/auth.py`), затем находит
или создаёт запись пользователя в БД (`app/api/deps.py::get_current_user`).

**Dev-режим:** если `TELEGRAM_BOT_TOKEN` не задан в `.env`, валидация
полностью пропускается, а все запросы атрибутируются фиксированному
служебному пользователю (id `0`) — это позволяет тестировать API и историю
через `/docs`/браузер без реального бота. В продакшене `TELEGRAM_BOT_TOKEN`
обязателен — без него любой сможет обращаться к API без проверки личности,
и все запросы будут писаться в один и тот же `Dev User`.

## Миграции

Схемой управляет Alembic — файлы в `alembic/versions/`. URL берётся из
`app.config.settings`, не из `alembic.ini`, поэтому база у приложения и у
миграций всегда одна и та же.

Миграции применяются автоматически при старте приложения
(`app/db.py::init_db`), отдельная команда при деплое не нужна. Логика такая:

- **чистая база** — накатывается всё с нуля до `head`;
- **база, созданная до Alembic** (есть таблицы, нет `alembic_version`) —
  сначала одноразовый прогон старого патчера колонок `_ADDED_COLUMNS`, затем
  `stamp 0001_baseline`, затем обычный `upgrade head`. Стампится именно
  baseline, а не `head`, чтобы `0002` реально отработала и дорасширила
  id-колонки до BIGINT, если старый код не успел этого сделать;
- **уже размеченная база** — просто `upgrade head`.

Если миграция не смогла взять блокировку (`lock_timeout`), приложение это
переживает: ревизия остаётся неприменённой, в лог уходит warning, приложение
стартует и обслуживает запросы, а следующий деплой пробует снова. Это
осознанно — предыдущая версия расширения колонок работала без таймаута и
однажды подвесила деплой на пять минут, положив всех пользователей в 502.

Добавить миграцию:

```bash
python -m alembic revision --autogenerate -m "что меняем"
python -m alembic upgrade head     # применить локально
python -m alembic check            # модели и миграции не разошлись
```

Список `_ADDED_COLUMNS` в `app/db.py` заморожен — это музейный экспонат для
дорастания старых баз, новые колонки идут только через ревизию.

## AI-толкование, дневное пожелание, подписка

### `GET /api/daily-message`
Одна мотивирующая фраза дня, кэшируется на календарные сутки (UTC) в таблице
`daily_messages` — одна и та же для всех пользователей, генерируется через
Groq или Anthropic API (если задан `GROQ_API_KEY` или `ANTHROPIC_API_KEY`),
иначе берётся из статичного списка в `app/ai/fallback.py`.

### `POST /api/spreads/{id}/interpret`
Платное подробное AI-толкование конкретного расклада (с учётом вопроса
пользователя и `interests` из профиля). Списывает одну единицу квоты через
`require_quota` — иначе `402 Payment Required`. Результат кэшируется на самой
записи расклада, так что повторный показ из истории бесплатен.

### `POST /api/spreads/{id}/follow-up`
Платный уточняющий вопрос по уже истолкованному раскладу. Пресетные вопросы
генерируются один раз на расклад и дедуплицируются по `question_key`;
произвольный текстовый вопрос (тарифы «Премиум» и «Магистр», список —
`FREE_TEXT_TIERS` в `app/subscriptions.py`) каждый раз новый.

### `POST /api/spreads/{id}/draw-extra`
Платное вытягивание ещё одной карты к уже существующему раскладу — тоже одна
единица квоты.

### `PATCH /api/profile/zodiac`, `/api/profile/patron-card`
Знак зодиака (спрашивается один раз в онбординге, где легко промахнуться) и
карта-покровитель — один из 22 старших арканов на выбор, `null` снимает
выбор. Карта проверяется по настоящей колоде
(`app/tarot/cards.py::MAJOR_ARCANA_IDS`), иначе сюда прошёл бы любой текст и
фронтенд попросил бы картинку `/cards/<мусор>.webp`. На расклады и их
толкование выбор не влияет — это оформление профиля.

### `GET/PATCH /api/profile`, `/api/profile/interests`
Чтение и обновление свободного текстового поля «темы» (`interests`),
которое подмешивается в промпт AI-толкования. Редактировать его из
приложения больше негде — блок «Ваши темы» убран с экрана профиля, — но
эндпоинт и само поле оставлены: у пользователей, успевших его заполнить,
значение продолжает влиять на толкование.

### `GET/POST /api/chat`
Чат с тарологом. `GET` отдаёт переписку, цену вопроса и текущий баланс.

`POST` принимает вопрос и отвечает потоком Server-Sent Events: события
`chunk` с кусками текста по мере генерации, затем `done` с id обеих реплик
и новым балансом — либо `error`. Поток, а не один ответ, потому что первые
слова готовы за доли секунды, а весь ответ на бесплатном тарифе может идти
несколько секунд; дождаться всего и потом «печатать» на экране значило бы
сложить два ожидания вместо того, чтобы убрать одно.

Отказы **до** начала генерации (пустой вопрос, запрещённая тема, не хватает
энергии) приходят обычными кодами HTTP, а не событиями: они случаются до
того, как отдан заголовок ответа.

Списание и запись делаются в **своей** сессии БД, а не в той, что пришла
зависимостью: сессия запроса закрывается, когда обработчик вернул
`StreamingResponse`, а генератор работает уже после этого.

Порядок действий в `POST` выбран так, чтобы человек не платил за неответ:
сначала модерация (та же `ensure_question_allowed`, иначе ограничения
обходились бы через чат), затем проверка, что энергии хватает, затем вызов
модели — и только на удавшемся ответе списание через
`require_quota(..., cost=CHAT_QUESTION_COST)`. Обратный порядок означал бы
списанные 5 единиц при отказе Groq. Плата за это — гонка: два одновременных
вопроса пройдут проверку и оба получат ответ. Размен осознанный, цена гонки —
один неоплаченный ответ.

В контекст уходят последние 10 реплик, профиль (знак зодиака,
карта-покровитель, «темы») и последний **разблокированный** расклад. Именно
разблокированный: карты неоплаченного расклада не должны утекать в чат, иначе
их можно прочитать в обход разблокировки.

Модель зовётся через `generate_chat_reply`, и это единственное место, где
цепочка провайдеров не применяется — только Groq. Чат даёт кратно больше
вызовов, чем всё остальное, и молчаливый переход на платный Anthropic выставил
бы счёт, которого никто не заказывал; вместо этого при 429 запрос ждёт и
повторяется.

### `GET /api/admin/users`, `GET /api/admin/users/{id}`
Поиск пользователя и его карточка — для разбора обращений в поддержку.
Поиск принимает числовой id, имя или username: в поддержку приходят
по-разному, а id знает только тот, кто уже смотрел логи.

Карточка показывает остатки энергии по источникам, подписку, все платежи с
их статусами и ленту оплачиваемых действий (расклады, вопросы в чат).
Неоткрытый расклад помечен отдельно и стоит 0 — это частый повод обращения
(«разложил, а толкования нет»).

Чего карточка **не** показывает и почему: журнала списаний энергии в базе
нет, хранятся только текущие остатки. Поэтому по ней видно, что человек
делал и за что платил, но не то, из чего сложился его нынешний баланс.
Понадобится такое — это отдельная таблица проводок, а не доработка
эндпоинта.

### Оплата: подписка через ЮKassa
Разовых покупок больше нет — доступ к платным функциям даёт квота, и
`require_quota` (`app/api/subscriptions.py`) тратит её в таком порядке:
сначала бесплатная дневная «энергия», затем реферальный бонус, и только
потом оплаченная подписка («Плюс» 599 ₽ / 70 разблокировок, «Премиум»
799 ₽ / 160 плюс свой вопрос к раскладу, «Магистр» 1199 ₽ / 300 плюс личный
чат с поддержкой). Так и приглашение друзей, и просто ежедневный заход в
приложение чего-то стоят даже без подписки.

Тарифы описаны в `app/subscriptions.py`; снятый с продажи помечается
`purchasable=False` и остаётся в `SubscriptionTier` навсегда — значение
тарифа лежит в базе строкой, и его резолвят и вебхук отложенного платежа, и
экран профиля действующего подписчика. `GET /api/subscriptions/tiers` отдаёт
фронтенду только то, что сейчас продаётся, чтобы цена на экране и цена в
счёте не могли разойтись.

`POST /api/subscriptions/create-payment` создаёт `SubscriptionPayment` в
статусе `pending` и платёж в ЮKassa, возвращая ссылку на оплату.
Подтверждение приходит на `POST /api/subscriptions/webhook`, и тело этого
запроса **не является доказательством оплаты**: платёж перепроверяется
прямым запросом к API ЮKassa (`app/yookassa/client.py`), и только после
этого запись переводится в `succeeded`, а подписке обновляются
`quota_total`/`period_end`. `GET /api/subscriptions/status` отдаёт фронтенду
текущий тариф, остаток квоты и энергию — включая `energy_daily_max`
(`DAILY_FREE_ENERGY`). Ёмкость нужна экрану, чтобы нарисовать баланс шкалой
аккумулятора: у суточной зарядки и у месячной квоты подписки потолок есть, а
у купленной и реферальной энергии его нет, и она показывается как «+N» сверх
шкалы.

Без `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` покупка подписки недоступна —
это внятная ошибка, а не падение. Для тестирования платного до появления
мерчант-аккаунта есть `POST /api/subscriptions/redeem-promo` с кодом из
`ADMIN_PROMO_CODE`.

### `POST /api/telegram/webhook`
Апдейты самого бота — обрабатывается `/start`, в ответ уходит сообщение с
кнопкой запуска Mini App. Вебхук нужно один раз зарегистрировать через
`setWebhook` (см. `DEPLOYMENT.md`), а секрет положить в
`TELEGRAM_WEBHOOK_SECRET`, чтобы отсекать запросы не от Telegram.
